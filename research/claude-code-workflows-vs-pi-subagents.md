# Claude Code Dynamic Workflows vs. Pi Subagents

> Research report — June 8, 2026
>
> Primary sources: [code.claude.com/docs](https://code.claude.com/docs), [changelog](https://code.claude.com/docs/en/changelog.md), [anthropics/claude-code GitHub repo](https://github.com/anthropics/claude-code)

---

## 1. Summary

- **Claude Code Dynamic Workflows** (released May 28, 2026, v2.1.154, "research preview") are JavaScript scripts that a runtime executes to orchestrate tens-to-hundreds of Claude subagents in the background. Claude writes the script for you; you can inspect, save, and rerun it. The plan lives in the script — not in Claude's turn-by-turn judgment.

- **Pi Subagents** are spawned Claude sessions running inside cmux panes. The parent LLM decides when and how to spawn them by calling `subagent()` or `parallel_subagents()` as tool calls within its own conversation turn. No script or declarative workflow file exists; orchestration is ad-hoc LLM reasoning from an AGENTS.md definition.

- **Headline difference**: CC Workflows move the orchestration plan into code (JavaScript), making it inspectable, repeatable, and capable of scaling to 1000 agents. Pi subagents keep the orchestration inside Claude's context window, making it flexible and conversational but not inherently repeatable or scale-bounded.

- CC Workflows are **real, released, and documented**. They are not vaporware. The feature shipped alongside Claude Opus 4.8 on May 28, 2026, in CC v2.1.154.

- The two systems are **architecturally complementary** — CC Workflows is a batch/pipeline primitive; pi subagents are a conversation/delegation primitive. They solve different problems despite surface similarity.

## 2. Claude Code Dynamic Workflows — Deep Dive

### 2.1 What It Is

> "A dynamic workflow is a JavaScript script that orchestrates subagents at scale. Claude writes the script for the task you describe, and a runtime executes it in the background while your session stays responsive." — [code.claude.com/docs/en/workflows](https://code.claude.com/docs/en/workflows.md)

A dynamic workflow is not a DAG definition, not a YAML config, and not a prompt template. It is a **JavaScript script** generated by Claude and executed by a dedicated runtime that's separate from the interactive conversation. The script spawns Claude subagents, coordinates them, and accumulates their results in script variables — not in Claude's context window.

| Version | Date | Event |

### 2.3 File Format and Location

Workflow scripts are **JavaScript files** (`.js`). They are stored in:

| Location | Scope | Notes |
|----------|-------|-------|
| `.claude/workflows/` | Project, committed to repo | Shared with team; runs as `/<name>` |
| `~/.claude/workflows/` | User, all projects | Personal; runs as `/<name>` |
| `~/.claude/projects/<session-dir>/` | Auto-generated per-run | Where every run's script lands on disk |

Bundled workflows are part of the Claude Code distribution itself (e.g., `/deep-research`).

**Saved workflows appear in `/` autocomplete** alongside skills and commands.

### 2.4 How Workflows Are Triggered

Three trigger paths:

1. **Keyword in prompt**: Type `ultracode` anywhere in your prompt. Before v2.1.160, the keyword was `workflow`. Natural-language requests ("use a workflow", "create a workflow that...") also work. The keyword is highlighted in violet.

   ```
   ultracode: audit every API endpoint under src/routes/ for missing auth checks
   ```

2. **Direct command**: Run a named workflow like `/deep-research <question>` or a saved custom workflow.

3. **Session effort level**: Run `/effort ultracode` to make Claude automatically plan a workflow for every substantive task in the session (combines `xhigh` reasoning with automatic orchestration).

**Dismissing the trigger**: Press `Option+W` (macOS) or `Alt+W` (Windows/Linux) to cancel a triggered workflow prompt. Configure "Workflow keyword trigger" in `/config` to disable keyword detection entirely.

### 2.5 Approval Flow

Before any run starts, Claude Code presents an approval dialog showing planned phases and these options:
- **Yes, run it**
- **Yes, and don't ask again for `<name>` in `<path>`** (stores consent)
- **View raw script** (inspect the JS before committing)
- **No**

`Ctrl+G` opens the script in your editor. `Tab` lets you adjust the task prompt before the run starts.

| Permission mode | When prompted |
|-----------------|--------------|
| Default / Accept Edits | Every run (unless per-workflow consent was given) |
| Auto mode | First launch only |
| Bypass permissions / `claude -p` / Agent SDK | Never |

Subagents spawned by the workflow always run in `acceptEdits` mode regardless of the session's mode.

### 2.6 How a Workflow Runs — Execution Model

The runtime executes the script in an **isolated environment, separate from the conversation**:

- **Script holds the plan**: loops, branching, and intermediate results live in script variables, not Claude's context.
- **Agents run in background**: up to 16 concurrent, 1,000 total per run.
- **No filesystem/shell access from the script directly**: the script only spawns agents. Agents do file reads/writes/bash.
- **No mid-run user input**: only agent permission prompts can pause a run.
- **Resumable within the session**: paused/stopped runs cache completed agent results; only incomplete agents re-run. This does not survive exiting Claude Code — next session starts fresh.
- **Script stored on disk**: `~/.claude/projects/<session-dir>/` contains the exact JS that ran, so you can read, diff, and edit it.

### 2.7 Step Composition

Because the script is plain JavaScript, composition uses standard JS constructs:

- **Sequential**: `const r1 = await agent(phase1Prompt); const r2 = await agent(phase2Prompt, r1);`
- **Parallel**: `const results = await Promise.all([agent(p1), agent(p2), agent(p3)]);`
- **Conditional**: standard `if/else` based on agent results
- **Loops**: `for` loops over file lists, etc.
- **Adversarial cross-checking**: run agent A, then agent B to review A's findings, filter on disagreements

The docs describe the quality pattern:

> "It can have independent agents adversarially review each other's findings before they're reported, or draft a plan from several angles and weigh them against each other, so you get a more trustworthy result than a single pass." — [workflows.md](https://code.claude.com/docs/en/workflows.md)

### 2.8 State Between Steps

Intermediate results live **in script variables**. The parent Claude session receives only the final synthesized report. This is the key difference from subagents inside a conversation, where every result lands in the context window.

### 2.9 Interaction with CC Subagents, Hooks, and Skills

- Workflow agents **are Claude Code subagents** — they use the same frontmatter format (`.claude/agents/*.md`).
- Hooks fire normally for each agent (e.g., `SubagentStop` hook fires when each workflow agent completes).
- Skills can be preloaded into workflow agents via the `skills` frontmatter field.
- The workflow script can reference agent definitions by name or construct agent configs inline.

### 2.10 `/effort ultracode`

Ultracode is a session-level effort mode:
- Combines `xhigh` reasoning with automatic workflow selection
- Claude decides whether each task warrants a workflow (rather than you typing `ultracode` explicitly)
- One request may spawn multiple sequential workflows
- Session-scoped (resets on new session)
- Only available on models that support `xhigh` effort (Opus 4.8; not on Haiku/Sonnet/Opus 4.7)

### 2.11 Bundled Workflow: `/deep-research`

The only bundled workflow shipped with CC:

```
/deep-research What changed in the Node.js permission model between v20 and v22?
```

What it does:
1. Fans out web searches across several question angles
2. Fetches and reads source pages
3. Cross-checks claims across sources using adversarial agent review
4. Votes on each claim; filters out claims that don't survive cross-checking
5. Returns one cited report

Requires the WebSearch tool.

### 2.12 Monitoring — `/workflows` View

```
/workflows
```

Shows: each phase, agent count, token totals, elapsed time. Navigate with arrow keys, `Enter` to drill in. Controls:

| Key | Action |
|-----|--------|
| `p` | Pause/resume |
| `x` | Stop agent or entire run |
| `r` | Restart selected agent |
| `s` | Save script as a named command |

### 2.13 Passing Input to Saved Workflows

Saved scripts receive a global `args` containing Claude-structured data from the invocation prompt:

```
> Run /triage-issues on issues 1024, 1025, and 1030
```

Claude passes `[1024, 1025, 1030]` as structured data — no string parsing required.

### 2.14 Disabling Workflows

```json
// ~/.claude/settings.json or managed settings
{ "disableWorkflows": true }
```

Or env: `CLAUDE_CODE_DISABLE_WORKFLOWS=1`. Toggle in `/config`. Admin: set in managed settings or the Claude Code admin settings page.

### 2.15 Concrete Example (from official docs)

The announcement prompt was:

```
> create a workflow that migrates every internal fetch() call to the new HttpClient wrapper
```

CC then:
1. Shows a "Dynamic workflow requested" indicator
2. Writes a JS orchestration script with phases (discover, migrate, verify)
3. Asks for approval
4. Runs agents in the background

Another example from the changelog that reveals the pattern:

> "a codebase-wide bug sweep, a 500-file migration, a research question that needs sources cross-checked against each other, and a hard plan worth drafting from several independent angles before you commit to one"

## 3. Pi Subagents — Deep Dive

### 3.1 What It Is

Pi subagents are full pi sessions spawned inside cmux pane terminals. Each subagent:
- Gets its own isolated context window
- Runs independently (fire-and-forget async)
- Calls `subagent_done` to self-terminate and return results to the parent session
- Is visible to the user in real-time via the cmux pane

Source: `~/.pi/agent/AGENTS.md`

### 3.2 Agent Definitions

Agents are Markdown files with YAML frontmatter at `~/.pi/agent/agents/<name>.md`:

```yaml
# ~/.pi/agent/agents/worker.md
---
name: worker
description: Implements tasks from todos
tools: read, bash, write, edit, todo
deny-tools: claude
model: github-copilot/claude-sonnet-4.6
thinking: minimal
spawning: false
auto-exit: true
system-prompt: append
---

# Worker Agent

You are a specialist in an orchestration system...
```

Fields include: `model`, `tools`, `deny-tools`, `thinking`, `spawning`, `auto-exit`, `system-prompt`.

The currently defined agents:
- `planner` — Interactive planning (Opus 4.7, medium thinking)
- `scout` — Fast codebase recon (Haiku)
- `worker` — Task implementation (Sonnet 4.6)
- `reviewer` — Code review (Opus 4.7)
- `validator` — Adversarial verification (GPT 5.5)
- `researcher` — Web + code research (Sonnet 4.6)
- `adversarial-reviewer` — Proof-of-wrongness review (Opus 4.7, medium thinking)

### 3.3 Spawning API (Tool Calls in LLM Turn)

The parent LLM spawns subagents via tool calls:

```typescript
// Single subagent
subagent({
  name: "Scout",
  agent: "scout",
  interactive: false,
  task: "Analyze the auth module..."
})

// Parallel fan-out
parallel_subagents({
  agents: [
    { name: "Scout: Auth", agent: "scout", task: "Analyze auth module" },
    { name: "Scout: DB", agent: "scout", task: "Map database schema" },
  ]
})

// Fork current conversation
subagent({
  name: "Iterate",
  interactive: true,
  fork: true,
  task: "Fix the bug where..."
})
```

### 3.4 Execution Model

- Each subagent is a **separate pi session** in a cmux pane
- **Fire-and-forget async**: parent session is notified when subagent calls `subagent_done`
- **Fork mode** (`fork: true`): clones the current conversation context into the subagent
- **Interactive** (`interactive: true`): user can interact with the subagent in real-time
- **No explicit orchestration script**: the parent LLM decides when/how to spawn based on its own reasoning about the task

### 3.5 Skills — The Procedural Instruction Layer

Skills (`~/.pi/agent/skills/` and `~/.agents/skills/`) are Markdown files with frontmatter loaded on demand:

```yaml
# SKILL.md
---
description: What this skill does...
---

## Instructions
Step 1...
Step 2...
```

Skills provide **procedural instructions** to the LLM — "when task X matches, load these instructions." Unlike CC skills, pi skills do not run in subagent contexts by default; they're loaded into the parent context when triggered.

### 3.6 Slash Command Orchestration

Slash commands (`/plan`, `/bbq`, `/iterate`, `/review`) are **prompt templates** that orchestrate subagent chains:

- `/plan` → investigate → scout → planner subagent → worker subagent → reviewer subagent
- `/bbq` → grill-with-docs session → adversarial review → plan
- `/review` → adversarial-reviewer subagent
- `/iterate` → fork current session for quick interactive fixes

These are defined as prompts in `~/.pi/agent/prompts/` and trigger chains of `subagent()` tool calls.

### 3.7 Context Isolation

Each subagent gets a fresh context window. The parent context accumulates only the `subagent_done` summary, not the full transcript of the subagent's work. This is semantically equivalent to CC's context isolation model, but the mechanism differs: pi uses process isolation (separate sessions), while CC uses a shared runtime with context boundaries enforced by the tool call / subagent boundary.

## 4. Optimization Axes Comparison

| Axis | CC Dynamic Workflows | Pi Subagents |
|------|---------------------|--------------|
| **Who holds the plan** | The JavaScript script | Parent LLM turn-by-turn judgment |
| **Orchestration style** | Declarative / code | Imperative / conversational |
| **Repeatability** | High — same script reruns exactly | Medium — LLM re-derives the plan each time |
| **Debuggability** | High — inspect the JS, diff runs, `/workflows` view with per-agent results | Medium — cmux pane visibility, but no unified run view |
| **Scale** | Up to 16 concurrent / 1,000 total per run | No hard bound, but typically 3–10 agents per "workflow" |
| **Determinism** | Medium — script is deterministic; agent outputs are not | Low — both orchestration and agent outputs vary run-to-run |
| **Flexibility** | Medium — JS is expressive, but must be generated by Claude | High — parent LLM can adjust plan dynamically based on intermediate results |
| **Context cost** | Low — intermediate results in script vars, not context | High — intermediate results accumulate in parent context |
| **Human-in-loop** | Pre-run approval; no mid-run input (except permission prompts) | Any time; parent LLM can pause and ask at any turn |
| **Composability** | Workflow scripts can be versioned, shared, composed | Skills/agents/slash commands combine freely but require LLM judgment |
| **Isolation model** | Script runtime + subagent context windows | Separate pi sessions (OS process level) |
| **Visibility to user** | `/workflows` TUI view | cmux panes, interactive by default |
| **Cost transparency** | Per-agent token counts visible in `/workflows` | No per-subagent token accounting visible |
| **Multi-model routing** | Per-script or per-agent model selection | Per-agent-definition model selection |
| **Latency** | Background (non-blocking conversation) | Background (fire-and-forget), user can watch |
| **State persistence** | Resumable within session; lost on exit | Not resumable; subagent dies cleanly |
| **Team sharing** | `.claude/workflows/` committed to repo | `~/.pi/agent/agents/*.md` in dotfiles / chezmoi |
| **Adversarial quality patterns** | First-class: script orchestrates cross-checking agents | Possible but manual: user must ask parent LLM to spawn adversarial reviewer |

## 5. What Each Gets Right

### 5.1 What CC Dynamic Workflows Gets Right

**The plan-as-code insight.** Moving orchestration into JavaScript is the right abstraction for large-scale, repeatable tasks. A script that says "run 200 agents, collect results, cross-check with 20 more agents, synthesize" is inspectable, debuggable, and version-controllable in a way that "please orchestrate this" is not.

**Adversarial quality patterns as first-class citizens.** The ability to build in independent verification, multi-angle drafting, and cross-checking at the script level produces more trustworthy results than a single-pass LLM judgment.

**Context efficiency.** Intermediate agent results in script variables instead of context window means a 500-agent run doesn't exhaust the parent's tokens.

**Resumability.** Pausing and resuming with cached agent results is a practical necessity for long-running jobs. Getting this right in v1 of the feature is good engineering.

**The approval UX.** Showing the planned phases before committing is exactly right. Script-inspectable before run is better than trusting a black box.

**Tight integration with CC subagents.** Workflows reuse the same `.claude/agents/*.md` format — no new primitives, just a new execution layer.

### 5.2 What Pi Subagents Gets Right

**Conversational flexibility.** The parent LLM can dynamically decide to spawn more agents, change strategy, or ask the user for clarification at any turn. This is genuinely more flexible than a pre-committed script.

**User visibility and interaction.** Every subagent runs in a cmux pane the user can watch in real-time. There's no "black box background job" — full transparency, with the option to interact with any subagent.

**Simple agent definition.** `~/.pi/agent/agents/worker.md` with frontmatter is minimal and understandable. The model, tools, and instructions are all in one readable file.

**Fork mode.** `fork: true` cloning the current conversation for focused iteration is a powerful primitive with no equivalent in CC workflows.

**Multi-model routing.** Using GPT-5.5 for validation while Sonnet handles implementation, all within one orchestrated flow, is trivially configured via agent definitions.

**Skills as just-in-time instruction loading.** Skills load procedural instructions only when relevant, keeping the base context clean. This is more granular than CC's approach of loading skills at session start.

## 6. What Each Gets Wrong / Limitations

### 6.1 CC Dynamic Workflows Limitations

**Requires Claude to write the script.** The quality of the workflow depends on Claude generating reasonable JavaScript. The script is inspectable, but most users won't edit raw JS. There's no user-facing DSL or template system yet.

**No mid-run input.** Long-running jobs are fully autonomous. If an unexpected situation arises (e.g., the code structure is different than expected), there's no way for the workflow to ask for guidance without the whole thing stopping. "For sign-off between stages, run each stage as its own workflow" is a clunky workaround.

**Session-scoped resumability.** If you close Claude Code mid-run, the next session starts fresh. For a 1-hour job, that's a meaningful risk.

**Context isolation is one-way.** Script sees only the final summaries from agents. There's no way for the script to say "if agent 47 found X, show me its raw output so I can make a branching decision." The model makes those decisions inside the script, which was written before the run.

**Research preview constraints.** 16 concurrent agent cap. The "up to 1000 agents" limit means unbounded loops in scripts will hit a hard cap and abort.

**Opaque JS API.** The docs don't publish the JavaScript API the script uses to spawn agents. There are no examples of actual generated script content in the documentation. This is a significant gap — you can't write scripts by hand without reverse-engineering what Claude generates.

**Tool allowlist friction.** Shell commands, web fetches, and MCP tools not in your allowlist can pause mid-run. For a 100-agent job, a single unexpected permission prompt blocks everything.

### 6.2 Pi Subagents Limitations

**Orchestration is not repeatable.** Each invocation of `/plan` or a chain of subagents relies on the parent LLM making the same decisions. There's no script to inspect, save, or replay. The same prompt may produce different orchestration choices.

**Context accumulation.** With many subagents reporting back to a single parent context, the parent context grows. Eventually compaction or context overflow becomes a concern.

**No scale-specific primitives.** There's no equivalent to "run 200 agents in parallel" with structured progress tracking. `parallel_subagents()` is designed for a small set of concurrent tasks, not large-scale pipelines.

**Per-subagent token cost invisible.** You can see the overall session cost, but there's no per-agent token accounting comparable to CC's `/workflows` view.

**No adversarial quality patterns in the protocol.** Cross-checking, multi-angle drafting, claim voting — these require the parent LLM to explicitly decide to do them each time. There's no `adversarial_review: true` flag.

**Subagents cannot spawn subagents** (when `spawning: false`). This is an intentional safety constraint but limits the ability to build deeply nested orchestration.

## 7. When to Use Which

### Use CC Dynamic Workflows when:

- **Scale > 10 agents** — codebase-wide audits, large file migrations, comprehensive research
- **Reproducibility matters** — you want the same orchestration to run again next week
- **Cross-checking is the point** — adversarial verification, multi-angle drafting
- **Context efficiency is critical** — the task would exhaust a context window if done turn-by-turn
- **The task is well-specified upfront** — you know what phases and agents are needed before starting
- **Team sharing** — commit `.claude/workflows/` for others to rerun

### Use Pi Subagents when:

- **The plan is uncertain** — you need to adapt based on intermediate findings
- **Human-in-loop is expected** — you want to interact with the subagent mid-task
- **Diverse model routing** — mixing GPT-5.5, Opus, Sonnet, Haiku in one flow
- **Small fan-out (2–8 agents)** — exploring multiple codebases, parallel audits, concurrent research angles
- **Fork mode** — iterating on the current conversation context in a focused sub-session
- **Interactive exploration** — planning sessions where the user collaborates with the agent
- **Conversation continuity** — the parent needs to react dynamically to each result

### The honest comparison:

CC Workflows is a **batch processing system** that happens to use LLM agents as compute units. Pi subagents is a **conversational delegation system**. These aren't direct competitors — they solve different problems at different scales.

## 8. Open Questions / Unknowns

**The actual JavaScript script API is not documented publicly.** The CC docs describe what workflows do, but they don't show a sample generated script or document the API for spawning agents programmatically from within a script. Questions unanswered:
- What function do you call to spawn an agent? `runAgent()`? `spawn()`?
- How are agent results typed? JSON? Markdown string?
- Can you spawn typed subagents (e.g., `agent: "code-reviewer"`) from within a workflow script?
- Can workflows themselves spawn subworkflows?

**No community examples found** at time of writing (June 8, 2026). The feature shipped 11 days ago. No GitHub repos with `.claude/workflows/*.js` examples were found via the GitHub API. The Claude Code repo itself does not have a `workflows/` directory.

**What "research preview" means for stability is unclear.** The docs say the feature requires v2.1.154+ and is in "research preview." The changelog shows rapid iteration (6+ releases touching workflows in 11 days). API stability is uncertain.

**Interaction with the Agent SDK is documented but not exemplified.** The docs say workflows work in `claude -p` and Agent SDK mode (no approval prompts), but there are no examples of programmatically submitting an `ultracode`-triggered task via the SDK.

**Cost model at scale is unclear.** The docs warn that "a single run can use meaningfully more tokens than working through the same task in conversation" but give no concrete estimate for a 100-agent run. This makes budgeting difficult.

**Agent concurrency limits on shared resources.** 16 concurrent agents is the stated cap "on machines with limited CPU cores." What is the cap on a powerful machine? Is it configurable?

**The `args` parameter schema is not documented.** The docs say Claude "passes structured data" but don't describe the schema Claude generates or how to type-annotate expected args in the script.
