# Lean Formal Review

Target: `$@` (resolve relative to the current Pi working directory, not this prompt file).

If no target is given, ask for one. Accept a directory, a few related files, or a named state machine. Read the target repository's instructions and test conventions first. Inspect the requested path and narrow it to **one** deterministic semantic boundary: explicit state/transitions, ownership, routing, retries, idempotency, permissions, or a pure transformation. If it spans multiple subsystems or depends chiefly on I/O, timing, or external services, explain the smaller boundary and stop or proceed only with that boundary. Do not model an entire app.

1. **Observe before formalizing.** Read implementation and relevant tests; write a short behavioral summary of inputs, outputs, state, transitions, invalid/terminal states, ordering, cancellation, duplicates, and failures where applicable. Separate intended rules from observed behavior. Select 3–6 domain properties (invariants, preservation, functional or sequence properties) whose failure would matter. List assumptions and excluded behavior. Do not silently discard a branch because it complicates a proof.
2. **Tooling and workspace.** Check `lean`, `lake`, and `elan`. Use the project's `lean-toolchain` if present, otherwise pin a Lean 4 version in an OS temporary directory (e.g. `mktemp -d "${TMPDIR:-/tmp}/formal-review.XXXXXX"`). Keep the model and report there, print the directory in the result; do not write a Lean project into the target repo by default. If Lean is absent, provide official elan setup instructions and stop rather than silently installing. On macOS `brew install elan-init` provides elan's `lean` and `lake` proxies; on Fedora use the official elan installer. A `lean-toolchain` file plus `Model.lean` needs no `lakefile` or Mathlib; run `lean Model.lean` from that directory. Add dependencies only if the particular proof needs them.
3. **Model semantics, not source syntax.** Prefer small explicit types and executable pure functions (`#eval`), optionally an inductive transition relation. Map every meaningful Lean definition to source paths and operations in a table. Make representative fixtures run through both Lean and the implementation where practical; show actual input/output pairs. State domain claims as theorems with readable proofs. Do not substitute a weaker claim for a hard proof. Capture real Lean exit statuses/output. If proof fails, classify it as THEOREM_FALSE, MODEL_INCOMPLETE, ASSUMPTION_MISSING, IMPLEMENTATION_BEHAVIOR_UNMODELED, PROOF_INCOMPLETE, or TOOLING_LIMITATION, with evidence; a tactic failure alone proves nothing.
4. **Find and check witnesses.** When a claim looks false, enumerate small states or use `#eval`, `decide`, or a concrete refutation. Record state/input, operation, observed Lean result, and violated claim. **Never call it an implementation bug before reproducing the same feasible behavior against actual code.** Run the real function/test with corresponding inputs, record command and output, then classify: CONFIRMED_IMPLEMENTATION_BUG, LEAN_MODEL_INCORRECT, LEAN_MODEL_INCOMPLETE, THEOREM_WAS_WRONG, MISSING_ASSUMPTION, EXPECTED_BEHAVIOR, or UNABLE_TO_REPRODUCE. Correct model/theorem if wrong.
5. **If confirmed:** add a regression test in the target's existing test framework, demonstrate failure before the fix where practical, make the smallest fix, then run the regression, relevant suite, Lean proofs, and witness checks again. Avoid changes outside this boundary. If modifying the target is inappropriate or unauthorized, report the confirmed reproduction and leave a proposed test/fix; do not claim it is fixed. Do not invent a cross-language framework for a few fixtures.
6. **Report in chat:** `# Lean Formal Review` with Target, Behavioral model, Implementation ↔ Lean mapping, Properties (claim, exact theorem, PROVED/FALSE/INCOMPLETE/UNCERTAIN), Proof results with command/exit status, Counterexamples/witnesses (Lean input, actual reproduction command/output, classification), Changes, Remaining uncertainty (finite bounds, informal correspondence, omitted behavior), and the disposable model path. Distinguish proven **model** properties from tested implementation behavior. A successful theorem never certifies that production code matches the model.

Reference example (not a general framework): in this dotfiles repo `tests/formal-review/command-safety/Model.lean` models the `rm` operand decision in `dot_pi/agent/extensions/command-safety/policy.ts`; from `tests/formal-review/command-safety/` run `lean Model.lean`. Use it only as a shape example, not as a substitute for reading the selected target.
